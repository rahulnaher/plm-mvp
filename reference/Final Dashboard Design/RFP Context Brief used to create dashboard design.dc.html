Mars Global RFP — PLM Reporting & Analytics MVP — AS-BUILT

Context Brief (Updated: As-Built)

This updates the original working brief to reflect what was actually built in the Claude Design prototype (Dashboard.dc.html), for handoff to development. Sections 1–3 and 6–7 are unchanged history; Sections 4, 5, 8 and 9 are updated to as-built; Sections 10–13 are new.

1. The RFP, in brief

Mars is establishing SAP PLM (cPLM) as the central enterprise system for product and packaging data, replacing standard SAP reporting with a purpose-built suite. The ask spans all Mars segments — Petcare, Snacking, Food — not a single division.

Scope

  • Design, build, and deploy 4–5 interactive business reports (confirmed mix: 2 complex, 2 medium, 1 simple) plus a landing page, covering Ingredients, Recipes/Finished Goods, Packaging Specs, Printed Specs, and Document Info Records (DIR).
  • Engineer Bronze → Silver → Gold data layers, a governed semantic layer, and a consumption layer, all inside Mars' High Confidential (HC) zone.
  • Recommend and architect the platform; provide implementation cost, hypercare, and long-term support estimates; outline a 12–24 month AI roadmap.

Key tenets

  • Clean, self-service reporting suite with a single landing page
  • Security via HC zone and role-based access control (RBAC)
  • High-scale concurrency, sub-30-second load SLA
  • Centralized semantic layer; optimized run and licensing costs
"A custom React application to handle complex, multi-level BOM explosions, enable highly interactive UX and meet performance SLAs without per-user licensing costs" — the platform choice argued in the solution deck, over native Power BI.

3. Proposed solution architecture

Three pillars: a custom React web app (chosen over native Power BI to render non-parent-child BOM structures without visual/licensing constraints), a medallion data architecture in Databricks Unity Catalog (Bronze/Silver/Gold/Semantic, entirely within the HC zone), and a phased AI roadmap (0–6mo MVP → 6–9mo automated data-health & anomaly detection → 9–12mo+ conversational spec exploration, contingent on GenAI governance approval).

Delivery: an 18–19 week phased timeline (design/data architecture → core solutioning → UAT → productionization → 2-week hypercare), handing off to a continuous "Core & Flex" DevOps pod.

Credibility anchor: Tiger previously built FRAD (Formulation Reporting & Analytics Database) for Mars pet-nutrition R&D on the same SAP PLM/MDG data model — ingredients, recipes, BOM hierarchies, where-used/explosion, nutrient compliance — which is the direct precedent for this MVP.

8. Synthetic data — as implemented

40 materials in MATERIALS, spanning FERT / REAL_SUB / SUB_RCP / ROH / VERP / PRNT, across Petcare/Snacking/Food and NA/EU/APAC/Global:

  • Petcare hero: Pedigree Adult Dry Chicken & Rice (15kg) — 3 regional FERT roots (US/EU/APAC), 1 master recipe, 1 vitamin/mineral sub-recipe, 4 raw materials, 3 packaging specs, 3 printed specs. 9 nodes per region tree.
  • Snacking hero: M&M's Milk Chocolate Sharing Pouch (250g) — 2 regional FERT roots (US/EU), 1 master recipe, 2 sub-recipes (shell, coating), 3 raw materials (cocoa, milk powder, sugar), packaging + print per region. 9 nodes per region tree.
  • Food hero: Ben's Original Express Rice (250g) — 2 regional FERT roots (EU/APAC), 1 master recipe, 1 seasoning sub-recipe, 2 raw materials (rice, spice blend), packaging + print per region. 7 nodes per region tree.
  • Catalog breadth: 5 additional standalone FERT items (Whiskas, Dove, Uncle Ben's, Cesar, Snickers) with no modeled BOM — populate Explorer/Hub counts and Compare's Attributes tab, but are not explodable in Traceability/Impact.
  • Segment-level counts for the Hub KPI strip (Total/Active/Phased Out per segment × region) are separate aggregate numbers, not derived from the 40-row catalog — they simulate the full portfolio (hundreds of specs) the catalog is a detailed sample of.
  • Masking: R&D Scientist — full access. General Associate — cost/kg and formulation % masked (shown as "–"). Finance & Business — formulation %/allergens masked, cost/kg and cost roll-ups visible.

9. Explorer state persistence — as implemented

Because the whole app is one continuously-mounted component, filter selections, checked rows, and the last drill-in target live in component state and are not reset when navigating to Traceability/Impact/Compare and back:

  • Filters: free text, material types, regions, segments, status — both the pending (unapplied) and applied filter sets survive.
  • Selected rows: the checkbox selection used for Compare persists until manually cleared.
  • Last drill target: clicking a spec ID, "Explode BOM", or "Analyze Blast Radius" stores that spec's ID and is used to default the Traceability root / Impact source picker on arrival.

11. Navigation & Hub KPI strip — as implemented

  • Sidebar: Mars PLM logo, PLM Hub, Specification Explorer, then an "Analysis" label over Top-Down Traceability / Bottom-Up Impact / Compare Specs. Active item highlighted.
  • Header: global search input (visual only, not wired — see Section 13), Role dropdown.
  • Hub KPI strip: Segment and Region are separate dropdown buttons, each opening a checkbox multiselect panel with its own Apply/Cancel — selections only take effect on Apply. The 5 KPI cards and the alerts list recompute from the applied selection; the Portfolio Health Trend chart is unfiltered (whole-portfolio view) by design.
  • Layout: fixed-height single-frame shell (sidebar + header don't scroll); only the main content area scrolls vertically. No horizontal scroll anywhere.

13. Open items / gaps for the developer

  • Search bar: not wired to any index or results view — needs a defined behavior (jump to Explorer with the term pre-filled? live results dropdown?).
  • Data scale mismatch: the Hub's segment/region KPI counts (hundreds of specs) are independent illustrative numbers, not aggregated from the 40-row Explorer catalog. A real build needs one consistent dataset (or an explicit rule for how "sample" vs "full portfolio" numbers relate).
  • RBAC is display-only: masking must be re-implemented as real server-side field authorization in production — the prototype's client-side mask is a UX reference only, not a security model.
  • BOM coverage: only 7 FERT roots (the 3 hero chains) have modeled BOM/impact data; a real build needs this sourced from actual PLM/MDG BOM tables for every material, not hand-authored trees.
  • Compare BOM tab depth: currently shows only each target's immediate children, not a full recursive diff of nested sub-recipes — confirm whether production needs deeper BOM diffing.
  • Notification bell and "View Full Portfolio"/row-link destinations: undefined — need target screens or removal.
